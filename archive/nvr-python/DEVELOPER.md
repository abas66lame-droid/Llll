# حارس العارضات — ملاحظات تقنية (لـ Claude Code أو المبرمج)

## البنية
- **اللغة:** Python 3.10+ بمكتبة الخادم القياسية (`http.server`) وقاعدة SQLite.
- **المتطلبات الخارجية:** `pillow` و`numpy` فقط. لا توجد أطر عمل أو OpenCV.
- **الواجهة:** صفحة HTML واحدة (`static/index.html`) تتحدث مع الـ API عبر JSON.
- **الخيوط (threads):** خيط لكل كاميرا (`CamWorker`)، وخيط `ticker` يفحص المهل المنتهية كل ثانيتين، وخادم ويب متعدد الخيوط.

## خوارزمية الكشف (`detector.py`)
1. الصورة تتصغّر إلى عرض 960 بكسل، وتتحول إلى قناة رمادية مُنعّمة 3×3 وقناتي لون: `R-G` و`(R+G)/2-B`.
2. اهتزاز الكاميرا يُقدَّر بإزاحة صغيرة (±8 بكسل) عبر ارتباط الحواف بدقة ربع الصورة.
3. منطقة العارضة تُقسَّم إلى خلايا: حوالي 20 خلية بالعرض، وحجم الخلية بين 10 و40 بكسل.
4. **لكل خلية** نجرّب 9 إزاحات صغيرة، ونحسب:
   - التشابه = `0.45·NCC(رمادي) + 0.55·NCC(الحواف)`، ونأخذ أفضل قيمة.
   - كمية التفاصيل (متوسط الحواف): في المرجع `tr`، وعند أفضل تطابق `tc`، والحد الأدنى والأعلى عبر الإزاحات.
   - أقل فرق في الإضاءة واللون عبر الإزاحات.
5. **التصنيف:**
   - **نقص `rem`:** تشابه < 0.5، والتفاصيل بعد < 6 وأقل من 0.55 من قبل، وفرق مطلق > 5.
   - **إضافة `add`:** العكس.
   - **تبديل `chg`:** تشابه < 0.3 مع اختلاف فعلي في التفاصيل أو اللون أو الإضاءة، أو فرق لون > 28، أو فرق إضاءة > 45.
6. **التجميع:** الخلايا «القوية» تكوّن المناطق، والضعيفة تُلحق بها فقط (حتى لا تندمج عارضتان). الحد الأدنى للمنطقة خليتان.
7. **النتيجة على صور الاختبار:** صفر إنذارات كاذبة في 720 مقارنة لصور فيها ضوضاء واهتزاز ±1 بكسل وتذبذب إضاءة ±3%.

## منطق الأحداث (`app.py`)
- **الاستقرار:** نقارن اللقطة الحالية بالسابقة داخل المنطقة. إذا تغيّر أكثر من 3% من الخلايا تُعدّ «حركة» ولا يُتخذ أي قرار. هذا يعني أن أي تغيير يجب أن يثبت في لقطتين متتاليتين.
- **المرجع:** مرجع لكل كاميرا يُحدَّث **لكل منطقة على حدة** (بدون هامش) بعد كل قرار، فيتكيّف النظام مع تغيّر المنتجات المستمر.
- **عند النقص `rem`:** يُنشأ حدث `pending` بمهلة `grace_minutes`، وتتمدد المهلة إذا كان هناك تنظيف مسجّل. يُطابَق مع بيع مسجّل خلال `sale_window_minutes`.
- **عند الإضافة أو التبديل:** إذا تداخلت المنطقة مع حدث مفتوح (تداخل > 35%)، يُعدّ رجوعاً:
  - إذا كان الحدث `pending` تصبح حالته `returned`.
  - إذا كان `incident` تصبح حالته `resolved` مع سبب `returned`.
  - وإلا يُسجَّل حدث معلومة (`added` أو `swap`).
- **التغيّر الكبير** (أكثر من 50% من المنطقة) يحتاج 3 قراءات مستقرة قبل اعتماده: معلومة `major`، أو تنبيه إذا كان ليلاً.
- **البيع** (`/api/sale`) يغلق تلقائياً أقدم الحالات المفتوحة في نفس العارضة: `pending`، أو `incident` خلال آخر 24 ساعة.
- **حالات الحدث:** `pending` ← `returned` | `sold` | `incident` ← `resolved` (بأحد الأسباب: sold، justified، theft، false، returned).

## الـ API
| الطريقة | المسار | الوصف |
|---|---|---|
| GET | `/api/state` | حالة الكاميرات والمناطق والعدادات |
| GET | `/api/frame/<cam>` | آخر لقطة JPEG |
| GET | `/api/events?status=open\|incident\|pending\|removals\|info\|all&zone=` | الأحداث |
| POST | `/api/events/<id>/resolve` | `{resolution, note, who}` |
| GET / POST | `/api/zones` | قراءة المناطق / إنشاء أو تعديل `{id?, camera, name, section, x, y, w, h}` (نِسَب 0..1) |
| POST | `/api/zones/<id>/delete` | حذف منطقة |
| POST | `/api/sale` | `{zone, qty, ref}`. **لا يحتاج رمز**، حتى يستخدمه الكاشير |
| POST | `/api/sales/import` | `{text}`: سطر لكل بيع بالشكل «منطقة، عدد، فاتورة» |
| POST | `/api/cleaning` | `{zone, minutes, who}`. **لا يحتاج رمز** |
| GET | `/api/report?days=14` | التقارير |
| GET / POST | `/api/config` | الإعدادات |
| POST | `/api/nvr/test` | `{host, port, user, password, https}` يرجع معلومات الجهاز والقنوات |
| POST | `/api/telegram/test` | رسالة اختبار تيليجرام |

**الحماية:** طلبات POST (عدا البيع والتنظيف) وقراءة الإعدادات تتطلب الترويسة `X-Pin` إذا كان `pin` مضبوطاً.

## هكفيجن ISAPI (`sources.py`)
- **المصادقة:** Digest مع Basic كاحتياط، عبر `urllib`. شهادات HTTPS ذاتية التوقيع مقبولة.
- **اللقطة:** يجرّب المسارات التالية بالترتيب، ويتذكر المسار الذي ينجح:
  - `/ISAPI/Streaming/channels/{ch}0{stream}/picture`
  - `/ISAPI/ContentMgmt/StreamingProxy/channels/{ch}0{stream}/picture`
- **القنوات:** من `/ISAPI/ContentMgmt/InputProxy/channels`، والاحتياط `/ISAPI/Streaming/channels`.
- **معلومات الجهاز:** من `/ISAPI/System/deviceInfo`.
- **الاختبار:** جُرّب على محاكي NVR بمصادقة Digest، شمل حالات كلمة سر خاطئة وقناة غير موجودة وجهاز غير متصل.

## خطوات التطوير المقترحة
1. **تجربة على كاميرا حقيقية** وضبط العتبات في `compare_zone` حسب الإضاءة وزاوية الكاميرا.
2. **تنبيهات أحداث الكاميرا الذكية:** الاستماع إلى `/ISAPI/Event/notification/alertStream` لاستقبال «Object Removal Detection» من الكاميرات التي تدعمه، كإشارة إضافية.
3. **مقطع فيديو للتنبيه:** سحب مقطع من الـ NVR عبر ISAPI ContentMgmt/search وplayback لوقت الحدث.
4. **ربط الكاشير الحقيقي:** إرسال البيع إلى `/api/sale` لحظياً، مع جدول يربط أصناف الكاشير بالعارضات.
5. **لوحة مركزية لعدة فروع:** خادم مركزي يجمع `/api/state` و`/api/report` من كل فرع، عبر VPN أو نفق آمن.
6. **ذكاء اصطناعي للحالات فقط:** عند كل `incident`، ترسَل صورة القص (`img_c`) إلى نموذج رؤية (مثل Claude API) لتسمية المنتج المفقود. هذا بضع عشرات من الطلبات يومياً، لا آلاف.
7. **الأداء:** النظام يحلل كل كاميرا كل 20 ثانية. لـ 30 إلى 60 كاميرا في الفرع يكفي كمبيوتر متوسط. لأعداد أكبر قسّم الكاميرات على أكثر من جهاز، أو زِد `poll_seconds`.
